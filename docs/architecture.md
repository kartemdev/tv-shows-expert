# Архитектура TV Shows Expert

Цель архитектуры — упростить доработку существующих фич: изменение поведения, данных или отображения должно затрагивать понятную локальную часть кода. Код организован в дерево компонентов, каждый из которых разделён на View и Presenter.

## View и Presenter

**View — любой React-компонент.** Он отвечает только за отображение JSX. Внутри остаются вызов собственного Presenter и JSX с привязкой готовых данных и обработчиков. Входные props необходимые для вычислений передаются в Presenter. Если пропс нужны только для отображения их можно сразу использовать в View (JSX).

JavaScript-логика во View запрещена: вычисления, преобразования коллекций, выбор состояния отображения, запросы, эффекты и реализация обработчиков находятся за пределами View. В JSX используются подготовленные значения и ссылки на методы, без inline-функций и вызовов, реализующих логику.

**Presenter — хук `use<ИмяКомпонента>Presenter`.** Он собирает данные из источников, связывает состояние, методы и инфраструктуру, подготавливает всё необходимое для View. Выбор отображаемых состояний и подготовка элементов списков также выполняются вне View; сами элементы оформляются отдельными View-компонентами.

В проекте Presenter всегда оформляется как хук с этим именем, даже если сейчас не вызывает хуки React. Это соглашение поддерживает цель архитектуры — быстро дорабатывать существующие фичи:

- **Единое место для логики.** По имени компонента сразу понятны имя и расположение его Presenter, независимо от сложности реализации.
- **Развитие без смены контракта.** Если понадобятся состояние, Context или эффекты, их можно добавить в существующий Presenter, сохранив его имя и способ вызова во View.

Presenter сразу вызывается по правилам хуков: на верхнем уровне View, без условий и циклов. Вызовы React-хуков добавляются по потребности сценария. Чистые вычисления можно выделять в обычные вспомогательные функции и вызывать из Presenter. React [допускает префикс `use` в расчёте на будущие вызовы хуков](https://react.dev/learn/reusing-logic-with-custom-hooks#should-all-functions-called-during-rendering-start-with-the-use-prefix); здесь этот подход закреплён для всех Presenter.

Пример View:

```tsx
export const ContactForm = () => {
  const {onSubmit, email, onEmailChange, submitLabel} = useContactFormPresenter();

  return (
    <form onSubmit={onSubmit}>
      <input
        value={email}
        onChange={onEmailChange}
      />
      <button type="submit">{submitLabel}</button>
    </form>
  );
};
```

У каждого компонента, включая дочерние и переиспользуемые, есть собственный Presenter. Его сложность определяется задачей компонента.

## Именование и состав папки компонента

- Каждый компонент находится в собственной папке. Одна папка содержит одну пару View/Presenter и принадлежащие ей вспомогательные файлы.
- Имя компонента, его папки и файла View совпадает и записывается в **PascalCase**: `ItemCard/ItemCard.tsx`.
- Стили компонента — CSS Modules рядом с View, с тем же именем в **PascalCase**: `ItemCard.module.css`.
- Presenter называется строго **`useItemCardPresenter`**, его файл — `useItemCardPresenter.ts`. Имя `usePresenter` без имени компонента не используется.
- Остальные файлы и папки именуются в **camelCase**: `formatPrice.ts`, `itemCardTypes.ts`. Имена вспомогательных функций и хуков также записываются в camelCase.
- Вспомогательные хуки и функции располагаются рядом с владельцем. Логические помощники используются в Presenter; помощники JSX отвечают только за отображение и не возвращают логику во View.

## Размер файлов и декомпозиция

Файл исходного кода содержит **не более 120 строк**, включая JSX. Файл читается как набор именованных абстракций, скрывающих детали реализации.

- Presenter связывает небольшие вспомогательные хуки и функции. Запросы, преобразования данных и обработка действий выделяются по ответственности; весь код не собирается в одном большом хуке.
- Большой View разбивается на дочерние компоненты. Каждый получает собственную папку и Presenter.
- Разделение проводится по смыслу, а не произвольными фрагментами ради лимита строк. Названия выделенных частей должны объяснять их назначение.

## Дерево компонентов и переиспользование

Компонент, используемый только одним родителем, располагается внутри папки этого родителя. Вложенность не ограничивается: дерево папок отражает реальные отношения компонентов.

Переиспользуемые компоненты размещаются в **`components` ближайшей общей ветки всех потребителей**. Например, если компонент нужен нескольким потомкам `Catalog`, его место — `Catalog/components`. Потребители находятся ниже владельца этой ветки; внешние ветки не обращаются к её внутренним компонентам.

Компоненты, общие для разных страниц или независимых фич, располагаются в `src/shared/components`. Если появляется новый потребитель за пределами текущей ветки, компонент поднимается к ближайшему общему предку. Размещать его выше необходимого заранее не нужно.

Пример дерева компонентов:

```text
src/
  components/
    Catalog/
      Catalog.tsx
      useCatalogPresenter.ts
      Filters/
        Filters.tsx
        useFiltersPresenter.ts
      ItemList/
        ItemList.tsx
        useItemListPresenter.ts
        ItemCard/
          ItemCard.tsx
          useItemCardPresenter.ts
          formatPrice.ts
          itemCardTypes.ts
      components/
        ActionButton/
          ActionButton.tsx
          useActionButtonPresenter.ts
```

Здесь `ItemCard` принадлежит `ItemList`, а `ActionButton` используется в `Filters` и `ItemList`, поэтому находится в `Catalog/components`.

## Как дорабатывать фичу

1. Найти компонент-владелец изменяемого поведения в дереве фичи.
2. Изменить поведение в его Presenter или вспомогательных хуках и функциях; изменение разметки внести во View.
3. При росте файла выделить осмысленную абстракцию или дочерний компонент с собственной парой View/Presenter.
4. При появлении переиспользования разместить компонент в `components` ближайшей общей ветки потребителей.
