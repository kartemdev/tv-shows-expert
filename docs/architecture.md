# Архитектура приложения

Цель архитектуры — упростить доработку существующих фич. Изменение поведения, данных или отображения должно затрагивать понятную локальную часть кода. Ответственность в коде распределяется по ролям **VIPER** (View, Interactor, Presenter, Entity, Router). Интерфейс образует дерево компонентов, у каждого из которых есть своя пара View и Presenter.

## V — View

**View — любой React-компонент.** Он отвечает только за отображение JSX. Внутри остаются вызов собственного Presenter и JSX с привязкой готовых данных и обработчиков. Props, необходимые для вычислений, передаются в Presenter. Props для отображения можно использовать прямо в JSX.

Вычисления, подготовка данных, выбор состояния отображения, запросы, эффекты и реализация обработчиков находятся за пределами View. В JSX используются подготовленные значения и ссылки на обработчики. Вспомогательный код, который вызывается из JSX, отвечает только за отображение. Например, он может отрисовать готовое значение, полученное из Presenter.

```tsx
export const ContactForm = () => {
  const { onSubmit, email, onEmailChange, submitLabel } = useContactFormPresenter();

  return (
    <form onSubmit={onSubmit}>
      <input
        value={email}
        onChange={onEmailChange}
      />
      <button type="submit">{submitLabel}</button>
    </form>
  );
};
```

## I — Interactor

**Interactor реализует вариант использования (use case).** В этой архитектуре роль Interactor выполняет **task**. Вариант использования описывает, как пользователь решает задачу с помощью автоматизированной системы. Пользовательская история формулирует цель, а вариант использования уточняет, какие входные данные нужны, какие действия выполняет система и какой результат получает пользователь. Это описание не зависит от выбранных инструментов.

Бизнес-правила действуют независимо от автоматизации. В коммерческой предметной области они помогают зарабатывать или экономить деньги. Критические бизнес-правила принадлежат сущностям и применяются во всех сценариях, которые вызывают соответствующие операции. Например, заказ определяет, допустима ли отмена при его текущем статусе.

Вариант использования описывает бизнес-правила конкретного приложения. Он определяет, как и когда применить критические правила одной или нескольких сущностей, чтобы получить результат сценария. Эту логику реализует `task`. Она задаёт порядок вызова операций сущностей, запросов и обновлений состояния.

Например, `cancelOrder` принимает идентификатор заказа, загружает заказ и вызывает его операцию отмены. Операция применяет правило допустимости отмены. Если заказ можно отменить, сценарий сохраняет новый статус и возвращает результат. Если отмена запрещена, сценарий возвращает причину отказа.

Один вариант использования имеет одну входную функцию, через которую его вызывают потребители. Имя начинается с глагола, например `login`, `logout` или `cancelOrder`. Отдельные шаги можно разложить на вспомогательные функции внутри task.

Task оформляется как обычная синхронная или асинхронная функция, которую можно вызвать вне React. Presenter извлекает нужные значения из событий интерфейса и передаёт их в task как входные данные сценария. При переходе на Vue или Angular новый интерфейс может вызывать ту же функцию.

### Доступ к состоянию из task

Task читает и обновляет состояние напрямую через базовый API стора, доступный вне React. Если стор открывает поля состояния как свойства, текущее значение читается через `store.currentUser`. В Redux для чтения используется `store.getState().currentUser`, а для обновления — `store.dispatch`. [API стора Redux](https://redux.js.org/api/store)

Сценарий запускается обычным вызовом функции. Последовательность шагов задаёт сама task через вызовы функций и `async`/`await`. Для этого достаточно базового API стора без Redux Thunk и Redux Saga. В примере `logout` отправляет действие сброса текущего пользователя после успешного завершения запроса.

```ts
export const logout = async () => {
  await logoutApi();
  store.dispatch(resetCurrentUser());
};
```

## P — Presenter

**Presenter связывает View, стор, сценарии приложения и инфраструктуру интерфейса.** Он получает состояние и операции стора, обрабатывает события интерфейса и вызывает нужную task. Presenter подготавливает данные для отображения и управляет локальным состоянием и эффектами интерфейса. Например, он может выбрать, показать ли сообщение об ошибке, и подготовить данные для списка. View строит список через `map`, а элемент списка оформляется отдельным View-компонентом со своим Presenter.

У каждого компонента, включая дочерние и переиспользуемые, есть собственный хук `use<ИмяКомпонента>Presenter`. По имени компонента можно определить имя и расположение Presenter. Достаточная для компонента реализация может состоять из нескольких простых вычислений. React-хуки добавляются по мере необходимости, когда появляются состояние, Context или эффекты. Имя и способ вызова сохраняются. [Документация React](https://react.dev/learn/reusing-logic-with-custom-hooks#should-all-functions-called-during-rendering-start-with-the-use-prefix)

Presenter вызывается на верхнем уровне View, вне условий и циклов. Вспомогательные вычисления можно выделить в обычные функции в `logic`. Если помощнику нужен доступ к состоянию или эффектам React, его можно оформить как вспомогательный хук и вызывать из Presenter.

## E — Entity

**Роль Entity выполняет стор.** Он предоставляет общее состояние сущностей и операции, которые применяют правила изменения данных. Для реализации стора подходит любой менеджер состояния или провайдер, который хранит состояние и открывает доступ к нему и операциям через Context.

Один сценарий может обращаться к операциям нескольких сущностей. Например, при оформлении заказа сценарий использует операции заказа и складских остатков, чтобы проверить возможность покупки и зарезервировать товар.

## R — Router

**Router отвечает за навигацию.** В веб-приложении эту роль может выполнять React Router. Маршруты объявляются при подключении маршрутизатора, например в точке входа или провайдере. Для перехода из компонента достаточно прямого вызова API маршрутизатора в Presenter.

Решение о переходе зависит от платформы и навигации конкретного интерфейса. Например, при нажатии кнопки выхода View вызывает обработчик из Presenter. Presenter вызывает `logout` и после успешного завершения выбирает переход. Веб-интерфейс может открыть страницу входа, а мобильный интерфейс может вернуться на начальный экран. Оба интерфейса используют один сценарий завершения сессии.

## Именование и состав папки компонента

Каждому компоненту принадлежит отдельная папка с одной парой View и Presenter. На верхнем уровне лежат файл View с JSX и его стили. Вспомогательные файлы располагаются рядом с кодом, который их использует. Папка `logic` объединяет код Presenter и локальных сценариев, а вложенная `logic/tasks` отделяет сценарии от логики интерфейса.

- Имя компонента, его папки и файла View совпадает и записывается в **PascalCase**, например `ItemCard/ItemCard.tsx`.
- Стили компонента — CSS Modules рядом с View, с тем же именем в **PascalCase**, например `ItemCard.module.css`.
- Файл Presenter называется `use<ИмяКомпонента>Presenter.ts`. Например, в `ItemCard/logic/useItemCardPresenter.ts` находится `useItemCardPresenter`. В той же папке `logic` хранятся вспомогательные хуки и функции этого Presenter.
- Локальная task может быть одним файлом, например `logic/tasks/cancelOrder.ts`. Если она занимает несколько файлов, их объединяет папка с именем task, например `logic/tasks/cancelOrder`. В ней находятся одна входная функция `cancelOrder` и вспомогательные шаги сценария. Такой же выбор между файлом и папкой действует для общих tasks.
- Остальные файлы и папки именуются в **camelCase**, например `formatPrice.ts` и `itemCardTypes.ts`. Имена вспомогательных функций и хуков также записываются в camelCase.

## Размер файлов и декомпозиция

Файл исходного кода содержит **не более 120 строк**, включая JSX. Файл читается как набор именованных абстракций, скрывающих детали реализации.

- Presenter связывает небольшие вспомогательные хуки и функции по их назначению. В них можно выделять подготовку данных для отображения, обработку событий и интерфейсные эффекты. В task выделяются самостоятельные шаги сценария, например подготовка входных данных или применение результата запроса.
- Большой View разбивается на дочерние компоненты. Каждый получает собственную папку и Presenter.
- При приближении к лимиту выделяйте части, у которых есть отдельная ответственность и понятное имя. Название должно объяснять, что делает выделенная часть.

## Дерево компонентов и переиспользование

Компонент, используемый только одним родителем, располагается внутри папки этого родителя. Вложенность не ограничивается: дерево папок отражает реальные отношения компонентов.

Переиспользуемые компоненты размещаются в **`components` ближайшей общей ветки всех потребителей**, а переиспользуемые сценарии — в её **`tasks`**. Из этих папок могут импортировать сам владелец ветки и его потомки. Например, сценарий, нужный `Catalog` и его дочернему компоненту `Filters`, находится в `Catalog/tasks` рядом с `Catalog/logic`.

Место выбирают по существующим потребителям. Если сценарий `resetFilters` нужен только `Filters`, он лежит в `Filters/logic/tasks`. Когда его начинает вызывать и `Catalog`, сценарий поднимают в `Catalog/tasks` и обновляют импорты. Так же поступают с компонентом при появлении потребителя за пределами его ветки.

Компоненты, используемые на разных страницах или в независимых фичах, размещаются в общем для приложения разделе интерфейса, например `shared/components`. Сценарий становится общим для приложения, когда его потребители находятся в независимых ветках без общего владельца внутри дерева.

Пример дерева компонентов с локальной и общей task.

```text
Catalog/
  Catalog.tsx
  Catalog.module.css
  logic/
    useCatalogPresenter.ts
    tasks/
      resetFilters.ts
  Filters/
    Filters.tsx
    logic/
      useFiltersPresenter.ts
      useFilterDraft.ts
      tasks/
        applyFilters/
          applyFilters.ts
          normalizeFilters.ts
  ItemList/
    ItemList.tsx
    logic/
      useItemListPresenter.ts
    ItemCard/
      ItemCard.tsx
      logic/
        useItemCardPresenter.ts
        formatPrice.ts
  components/
    ActionButton/
      ActionButton.tsx
      logic/
        useActionButtonPresenter.ts
```

`ItemCard` принадлежит `ItemList`. `ActionButton` используют `Filters` и `ItemList`, а `resetFilters` вызывают `Catalog` и `Filters`. Их общая ветка — `Catalog`. Сценарий `applyFilters` нужен только Presenter компонента `Filters`. Тот вызывает входную функцию `applyFilters`, которая делегирует нормализацию фильтров локальной функции `normalizeFilters`.

## Как дорабатывать фичу

1. Найти компонент-владелец изменяемого поведения в дереве фичи.
2. Изменить разметку во View, управление интерфейсом и переходы в Presenter, порядок действий сценария в task, а правила изменения данных в операциях сущности.
3. При росте файла выделить вспомогательную функцию, отдельный шаг сценария или дочерний компонент с собственной парой View/Presenter.
4. При появлении новых потребителей поднять компонент или task в `components` или `tasks` ближайшей общей ветки.
