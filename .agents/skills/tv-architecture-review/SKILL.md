# Ревью архитектуры

Прочитай [актуальную архитектуру](../../../docs/architecture.md) и [структуру проекта в README](../../../README.md). Проверяй запрошенный код и его реальные импорты и потребителей, чтобы определить владельца компонентов. Выполняй ревью без изменения файлов, если пользователь не запросил исправления.

Проверь:

- `src/components/` содержит интерфейс, `src/model/` — сущности, мапперы и общее состояние, `src/api/` — запросы, DTO и проверку ответов. API может использовать `shared`, но не импортирует модель, компоненты или страницы; модель не зависит от UI.
- Маппер принадлежит модели и передаётся в метод API параметром. DTO остаются за границей View; Presenter используют специализированные хуки модели. Provider в модели имеет собственные View/Presenter.
- View содержит собственный Presenter и JSX. Нет вычислений, преобразований списков, выбора состояний отображения, эффектов и реализации обработчиков. Прямое использование пропсов только для отображения допустимо.
- Presenter назван `use<ИмяКомпонента>Presenter`, даже если не вызывает хуки React; вызывается на верхнем уровне View без условий и циклов. Он подготавливает данные и методы, детали вынесены в осмысленные вспомогательные абстракции. Обычные чистые функции допустимы как его помощники.
- Папка и файл View совпадают с именем компонента в PascalCase; остальные файлы и папки используют camelCase. У каждого компонента есть своя пара View/Presenter.
- Приватный дочерний компонент вложен в родителя. Общие компоненты находятся в `components` ближайшей общей ветки; потребители не импортируют внутренности чужой ветки. Самостоятельные части сценария размещены в `src/components/`, общие UI-компоненты разных страниц или самостоятельных веток — в `src/shared/components`.
- Файлы исходного кода укладываются в 120 строк; декомпозиция сохраняет связность сценария и позволяет менять его локально.

Если нужна автоматическая проверка длины, выполни `pnpm check:lines` из корня. Она проверяет все исходники; отличай нарушения вне запрошенной области от результатов ревью. Biome и проверка типов не подтверждают архитектурное соответствие.

Для ревью конкретного PR учитывай его границы в [бэклоге](../../../backlog.md): реализация, явно отложенная в следующий PR, не является пропуском текущего. Существующие нарушения вне изменённого сценария отделяй от замечаний к проверяемой работе. Соответствие макету и полноту дизайн-спецификации проверяет [tv-design-review](../tv-design-review/SKILL.md), когда такое ревью запрошено.

В результате перечисляй подтверждённые нарушения: файл и строка, правило, последствие и минимальное исправление. Сначала указывай наиболее существенные. Если нарушений не найдено, сообщи это и назови проверенную область. Не выдавай предпочтения стиля за архитектурные требования.
